# Generation Task 并发管理方案

> 解决「千人同时发起 Node4 生图请求」场景下，**不让用户感受到延迟（loading 态可接受），同时不让模型被打爆** 的问题。

---

## 1. 概念边界（重要）

项目中存在两套任务概念，本方案只管理后者：

| 概念 | 含义 | 标识 |
|---|---|---|
| **task**（现有） | LangGraph 全流程：`input → node1 → node2 → node3 → node4 → done`，对应 DB `Task` 表 | `task_id`（短 UUID） |
| **generation_task**（本方案管理） | Node4 内部的单张图生图请求单元，**一 prompt 对应一张图** | `gen_task_id`（自动生成） |

generation_task 就是当前 `node4_graph.py` 里的 `work_item`，只是换个名字以强调它是"需要被 Redis 调度的独立生图请求"。

### generation_task 数据结构

```json
{
  "gen_task_id":     "gt_<task_id>_<index>",
  "parent_task_id":  "abc123def456",        // 关联到已有的 task_id
  "work_item_id":    "shot-01",             // 原 shot_id
  "prompt":          "一个穿红裙的模特...",
  "size":            "1024x1792",
  "ref_uris":        ["data:image/jpeg;base64,..."],
  "model_hint":      "qwen-image-3.0",
  "created_at_ms":   1726800000000
}
```

## 2. 现状痛点

当前 Node4 `_run_gen` 的并发控制是**单进程 asyncio.Queue + worker pool**：

```
uvicorn worker-0 ── asyncio.Queue + 8 worker
uvicorn worker-1 ── asyncio.Queue + 8 worker
uvicorn worker-N ── asyncio.Queue + 8 worker
       ↓
    合计 N × 8 并发 —— 模型真实承受 N 倍压力
```

两个致命问题：

1. **多进程不共享并发上限**：`settings.node4_gen_concurrency=8` 只约束了单进程，起 10 个 uvicorn worker 就等于 80 并发同时打模型。
2. **进程重启 = generation_task 全丢**：队列在内存里，挂了就没了。

---

## 3. 目标架构

**三层限流 + Redis 作为唯一调度中枢**：

```
                    ┌───────────────────────────────────┐
                    │ 第 1 层：Redis Semaphore          │
                    │ 控制「同时有多少个 Node4 在跑」     │
                    │ 例：全局上限 10                    │
                    └───────────────┬───────────────────┘
                                    │ acquire 成功
                                    ▼
  Node4._prepare() ─────────────────────────────────────────────
                                    │
                                    ▼
                    ┌───────────────────────────────────┐
                    │ 第 2 层：Redis List 队列           │
                    │ generation_task 序列化后 LPUSH    │
                    │ FIFO 全局池                       │
                    └───────────────┬───────────────────┘
                                    │
                    ┌───────────────┴───────────────────┐
                    ▼                                   ▼
          ┌──────────────────┐               ┌──────────────────┐
          │ Redis Worker-0    │               │ Redis Worker-N    │
          │ (BLPOP 阻塞等)    │               │ (BLPOP 阻塞等)    │
          └────────┬─────────┘               └────────┬─────────┘
                   │                                   │
                   ▼                                   ▼
                    ┌───────────────────────────────────┐
                    │ 第 3 层：Redis 令牌桶（Lua 原子）   │
                    │ 控制「每秒多少次模型 API 调用」       │
                    │ 例：每模型 1 QPS，桶容量 5           │
                    └───────────────┬───────────────────┘
                                    │ 放行
                                    ▼
                         模型 API（new-api 渠道）
```

三条 Redis key，语义清晰不混：

| Redis Key | 类型 | 作用 |
|---|---|---|
| `gen:semaphore:global` | String（INCR/DECR） | Node4 全局执行槽位（Semaphore） |
| `gen:queue:pool` | List | generation_task 全局池（FIFO） |
| `gen:token_bucket:{model}` | Hash（tokens, last_ms） | 单模型令牌桶 |
| `gen:result:{task_id}` | List | 某个商拍 task 的 generation_task 结果回传通道 |

---

## 4. 三层限流各自职责

### 第 1 层：Redis Semaphore（Node4 级并发闸门）

**管什么**：同时最多有多少个 LangGraph Node4 节点在执行。

**为什么需要**：令牌桶管速率，但单次生图耗时 5-15s，令牌桶 30 QPS 不代表你可以有 300 个 in-flight 请求（10 QPS × 10s = 100 in-flight）。Semaphore 是**硬上限兜底**。

**实现**：Lua 原子 `INCR + EXPIRE`，释放时 `DECR`。失败时 Semaphore 回滚，不污染状态。

**配置建议**：`node4_global_concurrency = 10`，TTL 120s（防进程崩溃导致槽位泄漏）。

### 第 2 层：Redis List（generation_task 全局池）

**管什么**：公平排队。所有 Node4 把要生的图序列化后 `LPUSH gen:queue:pool`，Redis Worker 集群 `BLPOP` 阻塞等。

**为什么需要**：队列天然跨进程、进程崩溃任务不丢、FIFO 保证公平。如果以后要做优先级（VIP 用户插队），把 List 换成 ZSET 即可，其他层不动。

### 第 3 层：Redis 令牌桶（模型级 QPS 控制）

**管什么**：**每秒允许多少次模型 API 调用**，强制匀速出流量。

**为什么需要**：Semaphore 控制的是"同时在跑多少个 Node4"，但一个 Node4 里会同时产生 N 张图的 generation_task（批内并发）。令牌桶是最终的"刹车"——不管上面压了多少 generation_task，每秒最多给 X 个放行。

**实现**：整段逻辑在 Lua 里原子执行，防并发取 token 的竞态。

**关键设计**：令牌桶**不是单一的一个**，而是**按模型拆分**——`gen:token_bucket:qwen-image-3.0`、`gen:token_bucket:doubao-pro` 各自独立。某个模型被限流了，直接跳过，让 generation_task 走降级链里的下一个模型（与 `image_gen_service.generate_single_image` 的降级逻辑天然融合）。

## 5. 延迟分析

generation_task 从"入队"到"被执行"的延迟构成：

| 阶段 | 耗时 | 用户可感知？ |
|---|---|---|
| Node4 里 `LPUSH gen_task × N` | ~1 ms / 张 | ❌ |
| Redis Worker `BLPOP` 到任务 | ~1 ms | ❌ |
| **令牌桶等待**（积压多时） | 0 ms ~ 几秒 | ⚠️ 用户感觉"一直在生成中" |
| Worker 调模型 API | 5 ~ 15 s | ✅ 正常耗时 |
| 结果回传 `LPUSH gen:result:{task_id}` | ~1 ms | ❌ |

**唯一需要用户等待的是"令牌桶积压"**——但这正是设计目标：不让用户请求把模型打爆，同时用户在 loading 态里自然等待。

### 千人场景数字估算

假设模型端硬限 **30 QPS**，单次生图 10s：

| 指标 | 值 |
|---|---|
| Redis Semaphore 全局槽位 | 10（同时最多 10 个 Node4） |
| 令牌桶每模型 QPS | 30（总） |
| 1000 个用户同时发起 → generation_task 数 | ~5000 张（每商拍平均 5 张） |
| 令牌桶匀速 30 QPS 跑完全部 | 5000 / 30 ≈ **167 秒 ≈ 2.8 分钟** |

用户感知：前 ~10 秒有 300 张图陆续出结果，后面平均每 33 ms 出一张。**不会出现大面积"全部卡死"的情况**——用户在 loading 态里看到的是"陆续有产出"，而不是"一堆请求被 503 拒掉"。

## 6. 进程崩溃安全

这是 asyncio.Queue 完全做不到的事。

| 组件 | 崩溃后会怎样 | 恢复方法 |
|---|---|---|
| **Node4 所在 uvicorn 进程** | LangGraph checkpoint 会残留"卡在 Node4" | `restart` 接口 → 从 checkpoint 续跑 → 再 LPUSH 一次 generation_task（Redis Worker 会看到重复 key 吗？见下） |
| **Redis Worker 进程** | `BLPOP` 的 generation_task 丢了 | Redis List 是 `LPUSH + BLPOP`，BLPOP 把元素弹出来后 Redis 就不保留了。**要保证不丢，必须用 Redis Stream 或 ACK 机制**——见下节 |
| **Redis 本身** | Redis 挂了 = 整个调度层瘫痪 | 这是"核心依赖"了，需要 Redis 高可用（哨兵/集群），但一般部署 Redis 的成本比重建一个调度层低得多 |

### generation_task 不丢的保障（关键细节）

Redis List 的 BLPOP 是"弹一下就没了"——Worker 拿到任务后如果自己崩了，这个 generation_task 就丢了。有两种解法：

**解法 A：用 Redis Stream（推荐）**

```
生产方（Node4）：XADD gen:stream:pool * gen_task_id ...
消费方（Worker）：XREADGROUP GROUP image-workers worker-0 COUNT 1 STREAMS gen:stream:pool >
完成后：XACK gen:stream:pool image-workers <message_id>
Worker 崩溃后组里的 PEL 自动保留
```

**解法 B：LPOPLPUSH 实现可靠队列**

```
生产方：LPUSH gen:queue:pool task
消费方：RPOPLPUSH gen:queue:pool gen:queue:in-flight:worker-0  ← 原子迁移
完成后：LREM gen:queue:in-flight:worker-0 task
崩溃恢复：启动时扫所有 gen:queue:in-flight:* → 重新 LPUSH 回 gen:queue:pool
```

本方案推荐 **解法 A（Redis Stream）**——Stream 是 Redis 5.0+ 原生功能，天然支持 consumer group + Pending Entries List，不需要自己写崩溃恢复逻辑。**把上面的 List 换成 Stream，其他层（Semaphore、令牌桶）完全不动**。

### 崩溃恢复时机

LangGraph checkpoint 恢复后，Node4 再次执行 `_run_gen`：
- 如果 Redis 里 `gen:result:{task_id}` 已经有部分结果 → 消费掉
- 如果还有 generation_task 没被处理（Worker 崩了）→ Stream 的 PEL 里还在，等 Worker 重新消费
- 如果全部没处理（Worker 崩在最前面）→ 可以选择：Node4 重新 XADD（保证能跑完），或者检查 Stream 里是否已有这个 gen_task_id（去重）

### 新增文件

| 文件 | 作用 |
|---|---|
| `wellflow/app/gen_dispatcher.py` | Redis 连接 + Semaphore Lua + 令牌桶 Lua（纯函数，无状态） |
| `wellflow/app/gen_worker.py` | Redis Worker 集群入口，启动期拉起 N 个 Worker 协程循环消费 Stream |
| `wellflow/app/config.py` 增 2 项 | `redis_url`、`node4_global_concurrency`、`image_model_tokens_per_sec` |

### 修改文件

| 文件 | 改什么 | 影响范围 |
|---|---|---|
| `wellflow/app/workflows/node4_graph.py` 的 `_run_gen` | 把本地 asyncio.Queue + worker pool 改成 Redis Stream 入队 + BLPOP/XRANGE 收结果 | 只影响 Node4 内部，输入输出契约不变，LangGraph checkpoint 不变 |
| `wellflow/app/runtime.py`（启动期） | 加一行 `start_gen_workers_in_background()` | 加一个协程池，不改现有逻辑 |
| `requirements.txt` | 加 `redis>=5.0` | 一个依赖 |

### 不改的文件（放心）

- `tasks.py` / `chat.py` / `outfit.py` / `mannequins.py` —— API 层不动
- `event_bus.py` / `sse.py` —— SSE 推送不动，Node4 里还是 `_eb(task_id, "node4_image_done", ...)`
- `TaskState` / checkpoint 相关 —— LangGraph 状态不动
- `image_gen_service.py` —— 降级链逻辑不动（但**调用方变了**，不是 Node4 内部 worker 直接调，而是 Redis Worker 调）

## 8. 关于"用户能不能接受排队"

用户 loading 态期间看到的应该是：

```
✅ Node 1 完成（VLM 识别商品属性）     耗时 6.5s
✅ Node 2 完成（营销文案生成）          耗时 8.2s  
✅ Node 3 完成（5 套生图 prompt）       耗时 3.1s
⏳ Node 4 生图中...（共 5 张）
   ├── shot-01 ✅ 完成 10.2s
   ├── shot-02 ✅ 完成 11.5s
   ├── shot-03 ⏳ 生成中
   ├── shot-04 ⏸️ 排队中（前面还有 23 张）
   └── shot-05 ⏸️ 排队中
```

这个信息完全可以通过**复用现有 SSE 事件**来表达：
- `node4_image_done` —— 每张图完成就推
- `node4_image_failed` —— 每张图失败就推
- 新增一个 `node4_queue_status` —— 定时推队列全局状态（可选，用 Redis ZCARD 查 pool 长度）

**前端不需要做任何新接口对接**——只是 Node4 里的"等待方式"从本地 worker pool 改成了 Redis Stream + Worker + 令牌桶，SSE 推出来的事件结构完全不变。

## 9. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| Redis 成为核心依赖 | Redis 挂了 = Node4 全挂 | 用哨兵/集群；做启动时 health check；Semaphore 和令牌桶都有 TTL 防泄漏 |
| generation_task 序列化体积大 | prompt + ref_uris（base64 图片数据）塞进 Stream | Stream 元素会很大（几 MB），但 Stream 比 List 好的一点是它有内部存储，不像 List 一次性全占内存。如果 ref_uris 太大，可以只存文件路径（已落盘），Worker 现场读文件 |
| LangGraph checkpoint 语义变化 | Node4 checkpoint 里可能残留 generation_task 状态 | 不变——我们只改 `_run_gen` 内部实现，不改它返回给 state 的 dict 结构 |
| 令牌桶 Lua 脚本调试 | Redis 集群模式下 Lua 脚本不能跨 slot | 把令牌桶 key 放在同一个 hash slot（加 `{}` 大括号），或用 `redis.pipeline` 绕过（放弃原子性？不行，令牌桶必须原子） |

## 10. 实施顺序建议

| 阶段 | 工作量 | 做什么 | 验证标准 |
|---|---|---|---|
| P0 | 2 天 | 引入 Redis + 只做 **第 1 层 Semaphore** —— 把 `node4_gen_concurrency` 变成跨进程共享 | 起 5 个 uvicorn worker，总共同时最多 10 个 Node4 跑 |
| P1 | 3 天 | 加 **第 2 层 Stream 队列** —— Node4 入队，Redis Worker 消费，结果回传到 `gen:result:{task_id}` | generation_task 真正跨进程调度；杀一个 uvicorn 进程，generation_task 不丢 |
| P2 | 2 天 | 加 **第 3 层令牌桶** —— 调模型前 Lua 原子取 token | 压测 100 并发 generation_task，模型端实际看到的 QPS = 令牌桶设定值 |
| P3（可选） | 1 天 | 队列长度监控 SSE 事件 | 前端展示"前面还有 N 张在排队" |

**P0 就足够验证整个架构方向**——如果 Semaphore 生效了（多 worker 并发真正受控），说明方向对了。再逐步叠 Stream 和令牌桶。
